# Обмен заказами с 1С

Версия схемы `1`. Go-типы — `internal/messaging/contracts/order.go`.

Состояние реализации:

- **1С → сайт** — работает: консьюмер читает `erp.orders`, обработчик —
  `internal/messaging/handler/order.go`, логика — `internal/service/order/erp.go`.
- **Сайт → 1С** — работает через transactional outbox (см. «Как сайт отправляет
  события»). По умолчанию включено; выключается настройкой
  `kafka.order_outbox.enabled: false` (`KAFKA_ORDER_OUTBOX_ENABLED`).

## Обзор

Обмен двухсторонний, через Kafka, два топика:

| Направление | Топик | События |
|---|---|---|
| Сайт → 1С | `store.orders` | `order.created`, `order.updated`, `order.paid`, `order.cancelled` |
| 1С → сайт | `erp.orders` | `order.status_changed`, `order.tracking_assigned` |

Заказ создаётся только на сайте. 1С получает его, ведёт сборку и отгрузку и
возвращает статус и трек-номер.

## Общие правила

- **Ключ сообщения** — `order_id` заказа строкой
  (`"8f2f4f0c-3b0e-4f43-9a52-2d1a6b0d9c10"`). События одного заказа попадают в
  одну партицию и читаются по порядку.
- **Значение** — JSON в UTF-8, имена полей в `snake_case`.
- **Идентификатор заказа в обмене** — `order_id` (uuid). 1С получает его в
  `order.created` и возвращает в каждом своём сообщении. `order_number` — номер
  для людей (целое, начиная с 100000), передаётся только в `order.created`
  справочно.
- **Деньги** — строка с точкой: `"1290.00"`. Не число с плавающей точкой, не запятая.
- **Время** — RFC 3339 со смещением: `"2026-10-11T12:30:00+03:00"`.
- **Доставка at-least-once**: сообщение может прийти повторно. Получатель обязан
  отбрасывать уже обработанный `event_id`.
- Необязательные поля при отсутствии значения не передаются. Незнакомые поля
  получатель игнорирует — добавление нового необязательного поля версию не меняет.

## Конверт

Любое сообщение в обоих топиках обёрнуто одинаково:

```json
{
  "event_id": "5b0c1f0e-6f0a-4a57-9d3e-0c1c5a3f8a11",
  "event_type": "order.created",
  "schema_version": 1,
  "occurred_at": "2026-10-11T12:30:00+03:00",
  "payload": { }
}
```

| Поле | Тип | Описание |
|---|---|---|
| `event_id` | uuid | Уникален для события, по нему делается дедупликация |
| `event_type` | string | Определяет формат `payload` |
| `schema_version` | number | Версия контракта, сейчас `1` |
| `occurred_at` | datetime | Когда событие произошло у отправителя |
| `payload` | object | Тело события |

Тип события всегда читается из `event_type` конверта — в `payload` он не
дублируется. Примеры ниже показывают сообщение целиком, как оно лежит в топике;
таблицы полей описывают содержимое `payload`.

## Сайт → 1С (`store.orders`)

### `order.created`

Полный снимок заказа на момент оформления. Тот же формат `payload` у
`order.updated`.

```json
{
  "event_id": "5b0c1f0e-6f0a-4a57-9d3e-0c1c5a3f8a11",
  "event_type": "order.created",
  "schema_version": 1,
  "occurred_at": "2026-10-11T12:30:00+03:00",
  "payload": {
    "order_id": "8f2f4f0c-3b0e-4f43-9a52-2d1a6b0d9c10",
    "order_number": 100042,
    "version": 1,
    "user_id": "c7a1e1c2-55f4-4f0e-b0a3-0e6f6f1f2a33",
    "source": "checkout",
    "status": "pending",
    "payment_status": "unpaid",
    "payment_method": "card",
    "email": "buyer@example.com",
    "phone": "+79990001122",
    "shipping": {
      "city_name": "Москва",
      "address": "ул. Ленина, д. 1, кв. 10",
      "postcode": "101000",
      "recipient": "Иванов Иван",
      "method": "pickup_point",
      "provider": "cdek",
      "tariff_code": "136",
      "point_code": "MSK123"
    },
    "currency": "RUB",
    "subtotal": "2580.00",
    "discount_total": "0.00",
    "shipping_total": "350.00",
    "tax_total": "0.00",
    "grand_total": "2930.00",
    "items": [
      {
        "product_id": "0b6f5d6e-0d4b-4d0b-9c58-5b8c7a1d2e44",
        "variant_id": "f3a9b0c1-7a55-4a0e-8d11-9c2b3d4e5f66",
        "external_id": "19c9f92b-81de-11f1-b9d9-00155ddf6800",
        "sku": "APPL-IP15P-256-BLK",
        "name": "iPhone 15 Pro 256GB Black",
        "unit_price": "1290.00",
        "quantity": 2,
        "line_total": "2580.00"
      }
    ],
    "comment": "Позвонить перед доставкой",
    "created_at": "2026-10-11T12:30:00+03:00"
  }
}
```

| Поле | Обяз. | Описание |
|---|---|---|
| `order_id` | да | uuid заказа, идентификатор заказа во всём обмене |
| `order_number` | да | Номер заказа для людей (в письмах покупателю, в админке). Справочно |
| `version` | да | Версия заказа, растёт при каждом его изменении. Снимок с версией меньше уже применённой — устаревший, его можно отбросить |
| `user_id` | нет | Отсутствует у гостевого заказа |
| `source` | да | `checkout` — обычное оформление; `quick` — быстрый заказ (только имя и телефон, остальное собирает менеджер) |
| `status` | да | Текущий статус заказа. В `order.created` — `pending` или `new` (для `quick`) |
| `payment_status` | да | `unpaid` / `paid` / `partially_refunded` / `refunded` / `failed` |
| `payment_method` | нет | Способ оплаты |
| `email` | да | |
| `phone` | нет | |
| `shipping.city_name`, `address`, `recipient` | да | Снимок адреса; у `quick`-заказа могут быть пустыми строками |
| `shipping.postcode`, `method` | нет | |
| `shipping.provider`, `tariff_code`, `point_code` | нет | Перевозчик, тариф и ПВЗ, выбранные при оформлении |
| `currency` | да | ISO 4217, сейчас всегда `RUB` |
| `subtotal`, `discount_total`, `shipping_total`, `tax_total`, `grand_total` | да | `grand_total = subtotal - discount_total + shipping_total + tax_total` |
| `items[].external_id` | нет | `external_id` товара из выгрузки `store.products` — по нему 1С сопоставляет номенклатуру. Отсутствует у товара, заведённого на сайте вручную |
| `items[].product_id`, `variant_id`, `sku` | нет | |
| `items[].name`, `unit_price`, `quantity`, `line_total` | да | Снимок позиции на момент заказа |
| `comment` | нет | Комментарий покупателя |
| `created_at` | да | |

### `order.updated`

Заказ изменён после создания. `payload` — полный снимок заказа в том же формате,
что у `order.created`, уже с учётом изменения: 1С перезаписывает документ
целиком, а не применяет разницу.

Отправляется, когда менеджер в админке:

- меняет состав заказа — добавляет или убирает позицию, меняет количество
  (меняются `items`, `subtotal`, `grand_total`);
- меняет детали — контакты, адрес, перевозчика, способ оплаты, комментарий
  (при смене доставки меняются `shipping_total` и `grand_total`);
- подтверждает быстрый заказ: `status` переходит из `new` в `pending`, в снимке
  появляются адрес и доставка, которых не было в `order.created`.

```json
{
  "event_id": "e2b7c1d4-3a5f-4e6b-9c8d-7f6e5d4c3b04",
  "event_type": "order.updated",
  "schema_version": 1,
  "occurred_at": "2026-10-11T12:50:00+03:00",
  "payload": {
    "order_id": "8f2f4f0c-3b0e-4f43-9a52-2d1a6b0d9c10",
    "order_number": 100042,
    "version": 4,
    "...": "остальные поля — как в order.created"
  }
}
```

Оплата, отмена и возвраты `order.updated` не вызывают — оплата и отмена идут
своими событиями ниже, возвраты пока не отправляются.

```json
{
  "event_id": "c9e8b7a6-5d4c-4b3a-9e2f-1a0b9c8d7e02",
  "event_type": "order.cancelled",
  "schema_version": 1,

  "payload": {
    "order_id": "8f2f4f0c-3b0e-4f43-9a52-2d1a6b0d9c10",
    "reason": "Отменён покупателем",
    "cancelled_at": "2026-10-11T13:05:00+03:00"
  }
}
```

### Как сайт отправляет события

- Событие записывается в таблицу `order_outbox` **в той же транзакции**, что и
  изменение заказа: если заказ создан, изменён, оплачен или отменён — событие есть; если
  транзакция откатилась — события нет.
- Воркер-релей (`internal/messaging/worker/order_outbox.go`) раз в
  `kafka.order_outbox.interval` (по умолчанию 2 с) публикует неотправленные
  события в Kafka строго в порядке записи и отмечает их отправленными после
  подтверждения брокера.
- Если брокер недоступен, событие остаётся в очереди и отправляется повторно;
  следующие события ждут за ним — порядок не нарушается. Число попыток и
  последняя ошибка — в колонках `attempts`, `last_error`.
- Событие может прийти в 1С повторно (сбой между отправкой и отметкой) —
  отсюда требование дедупликации по `event_id`.
- Отправленные события хранятся `kafka.order_outbox.retention` (по умолчанию
  7 дней), затем удаляются.
- Пока обмен выключен, события не записываются вовсе: заказы, созданные в это
  время, в 1С после включения не попадут.

## 1С → сайт (`erp.orders`)

### `order.status_changed`

```json
{
  "event_id": "7f3e2d1c-0b9a-4e8d-b7c6-5a4f3e2d1c03",
  "event_type": "order.status_changed",
  "schema_version": 1,
  "occurred_at": "2026-10-11T12:29:40+03:00",
  "payload": {
    "order_id": "8f2f4f0c-3b0e-4f43-9a52-2d1a6b0d9c10",
    "external_id": "ЗК-000123",
    "status": "shipped",
    "comment": "Передан в СДЭК",
    "changed_at": "2026-10-11T12:29:40+03:00"
  }
}
```

| Поле | Обяз. | Описание |
|---|---|---|
| `order_id` | да | uuid заказа из `order.created` |
| `external_id` | нет | Номер или GUID документа заказа в 1С, до 128 символов. Сайт запоминает первое полученное значение и дальше его не меняет |
| `status` | да | `processing` / `shipped` / `delivered` |
| `comment` | нет | Попадает в историю статусов заказа |
| `changed_at` | да | Когда статус изменился в 1С |

Сайт применяет статус через свой граф переходов:

```
paid → processing → shipped → delivered
```

- Повтор текущего статуса — не ошибка, сообщение пропускается.
- Недопустимый переход (например, `shipped` для неоплаченного заказа или шаг
  назад) сайт не применяет и пишет в лог. Пропускать шаги нельзя: перед
  `shipped` должен прийти `processing`. `external_id` из такого сообщения
  всё равно сохраняется.
- `paid`, `cancelled`, `refunded` от 1С не принимаются — оплату и возвраты ведёт
  сайт.

### `order.tracking_assigned`

```json
{
  "event_id": "0d9f6c9a-0a35-4b0e-8f3b-6a4a3c0f7b22",
  "event_type": "order.tracking_assigned",
  "schema_version": 1,
  "occurred_at": "2026-10-11T12:59:00+03:00",
  "payload": {
    "order_id": "8f2f4f0c-3b0e-4f43-9a52-2d1a6b0d9c10",
    "tracking_number": "10012345678",
    "provider": "cdek",
    "tracking_url": "https://www.cdek.ru/ru/tracking?order_id=10012345678",
    "assigned_at": "2026-10-11T12:59:00+03:00"
  }
}
```

| Поле | Обяз. | Описание |
|---|---|---|
| `order_id` | да | uuid заказа из `order.created` |
| `tracking_number` | да | Трек-номер перевозчика, до 128 символов |
| `provider` | нет | Код перевозчика, до 32 символов; если не передан — считается перевозчик из заказа |
| `tracking_url` | нет | Ссылка на отслеживание, до 512 символов |
| `assigned_at` | да | |

Трек-номер статус заказа не меняет — `shipped` передаётся отдельным
`order.status_changed`. Повторное событие по тому же заказу заменяет трек-номер.

### Как сайт обрабатывает входящие сообщения

- Обработанный `event_id` запоминается; повторное сообщение с тем же
  `event_id` пропускается.
- Сообщение, которое сайт не может применить никогда — битый JSON, неизвестный
  `event_type`, другая `schema_version`, нет обязательного поля, превышена
  длина, заказ не найден, недопустимый переход — пишется в лог и считается
  обработанным. Ответа об ошибке 1С не получает; чтобы исправить, нужно
  отправить новое сообщение с новым `event_id`.
- При сбое на стороне сайта (например, недоступна БД) сообщение не
  подтверждается.

## Открытые вопросы

- Может ли 1С отменять заказ (нет товара на складе)? Сейчас не принимается:
  отмена оплаченного заказа тянет за собой возврат денег.
- Нужно ли 1С событие о возвратах (полных и частичных). Сейчас не отправляется.
- Нужны ли реквизиты юрлица (ИНН, КПП) — сейчас их в заказе нет.
